### 2.2 厂商/框架对"速度是否够用"的官方判据

| 判据 | 数字 | 来源 |
|---|---|---|
| 人类阅读速度上限 | **10 tokens/s/用户 ≈ 450 words/min**，"快于常人阅读速度"（即再快用户也读不完） | [Databricks](https://www.databricks.com/blog/llm-inference-performance-engineering-best-practices) |
| 商用 API 首字延迟量级 | 最优模型 **0.43–0.46 s** | [Artificial Analysis](https://artificialanalysis.ai/models) |

### 2.3 人机交互经典阈值（Nielsen，1993 起沿用，原文引用 Miller 1968 / Card et al. 1991）

| 阈值 | 原文结论 | 来源 |
|---|---|---|
| **0.1 s** | "the limit for having the user feel that the system is reacting **instantaneously**"，无需任何反馈 | [NN/g: Response Times: The 3 Important Limits](https://www.nngroup.com/articles/response-times-3-important-limits/) |
| **1.0 s** | "the limit for the user's **flow of thought to stay uninterrupted**"；用户会注意到延迟，但无需特殊反馈 | 同上 |
| **10 s** | "the limit for keeping the user's **attention focused on the dialogue**"；超过则用户会转去做别的事 | 同上 |
| **>10 s** | "Anything slower than 10 seconds needs a **percent-done indicator** as well as a clearly signposted way for the user to **interrupt** the operation" | 同上 |
| **2–10 s** | "For reasonably fast operations, taking between **2 and 10 seconds**, a true percent-done indicator may be **overkill**" | 同上 |
| **>1 s 的处理** | "For delays of more than 1 second, indicate to the user that the computer is working on the problem, for example by changing the shape of the cursor" | 同上 |

> 另：Google RAIL 模型原文（web.dev/articles/rail）本次**网络不可达**，故未引用；NN/g 文中的 0.1/1/10 s 阈值本身即引自 Miller(1968)、Card et al.(1991)，可作为一手替代。

### 3.2 学术侧：多步/多 agent 串行调用的延迟结构与量化

| 结论 | 内容（原文要点） | 来源 |
|---|---|---|
| 多 agent 的端到端延迟由"关键执行路径"决定，而非总成本 | "In MAS, **end-to-end latency is governed by the critical execution path**, so reducing total cost alone does not reliably reduce latency"；"multi-step execution and repeated model invocations" 带来高推理延迟 | [LAMaS: Learning Latency-Aware Orchestration for Multi-Agent Systems (arXiv 2601.10560)](https://arxiv.org/abs/2601.10560) |
| 多阶段工作流 = 每阶段一次 LLM 调用，输出进入后续 context | "each stage is an LLM call whose output becomes part of context for subsequent steps" | [Chimera: Low-latency Multi-Agent Serving (arXiv 2603.22206)](https://arxiv.org/abs/2603.22206) |
| 长程 agentic 任务的上下文规模 | 多轮 agentic 任务 "conversations can span **dozens of API calls** with increasingly large context windows"，评测集为 DeepResearch Bench | [Don't Break the Cache: prompt caching for long-horizon agentic tasks (arXiv 2610.38809)](https://arxiv.org/abs/2610.38809) |

## 5. 关键对比：纯规则 / 确定性引擎（非 LLM）的响应时间量级

| 指标 | 数字（原文） | 来源 |
|---|---|---|
| 低延迟策略判定的**预算量级** | "a microservice API authorization decision might have a budget in the order of **1 millisecond**" | [OPA: Policy Performance](https://www.openpolicyagent.org/docs/latest/policy-performance/) |
| RBAC 判定单元基准（benchstat，10 次重复） | **29.8 µs ±18%** / **32.0 µs ±35%** per op；`timer_rego_query_eval_ns/op` = **25.0k ns（25 µs）** | 同上 |
| 单次 `opa test` 计时 | `data.rbac.test_user_has_role_dev: PASS (**605.076µs**)`、`..._negative: PASS (**318.047µs**)`（含进程启动） | 同上 |
| 逐行 profile（首次执行，未预热） | 顶层 `data.rbac.allow` = **237.126 µs**；子规则 3.1–25.75 µs | 同上 |
| 稳态 profile（多次统计） | `data.rbac.allow`：min **5.208 µs** / mean **9.008 µs** / 90% **25.525 µs** / 99% **27 µs** | 同上 |

> 量级结论：确定性规则引擎为 **µs–ms 级（10⁻⁶–10⁻³ s）**，比任何 LLM 推理路径（10⁻¹–10⁰ s 首字）低 **2–3 个数量级**；OPA 官方把"低延迟策略判定"的工程预算直接定义为 **1 ms**。
> **未找到可靠公开数据**：专门的"福利资格判定 / eligibility engine"（如 IBM ODM、Drools、FICO Blaze）官方性能基准；上述 OPA 数据是通用策略引擎中最接近且可引用的公开值。

## 6. 分档结论（按业界公开依据划分）

| 档位 | 依据（可引用来源） | 公开数据支撑 |
|---|---|---|
| **< 1 s = 即时（instantaneous）** | NN/g：0.1 s 为"感觉系统即时反应"的上限；1.0 s 为"思维流不被打断"的上限 | [NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)；商用 API 首字延迟最优 **0.43–0.46 s**（[AA](https://artificialanalysis.ai/models)） |
| **1–3 s = 流畅（flow 不中断）** | NN/g："a delay of 0.2–1.0 seconds does mean that users notice the delay"；1.0 s 内无需特殊反馈 | [NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/) |
| **3–10 s = 可容忍（attention 仍聚焦）** | NN/g：10 s 为"保持注意力在对话上"的上限；且 **2–10 s** 区间"a true percent-done indicator may be overkill"（即无需进度条，只需"正在处理"提示） | 同上 |
| **> 10 s = 必须进度反馈** | NN/g 原文："Anything slower than 10 seconds needs a percent-done indicator as well as a clearly signposted way for the user to interrupt the operation" | 同上 |
| **> 30 s = 后台任务（异步 + 通知）** | Deep research 类产品的公开耗时直接落在该区间：OpenAI **5–30 min**、Perplexity **<3 min**，且产品形态为"完成后发通知" | [TechCrunch 2025-02-02](https://techcrunch.com/2025/02/02/openai-unveils-a-new-chatgpt-agent-for-deep-research/)、[TechCrunch 2025-02-15](https://techcrunch.com/2025/02/15/perplexity-launches-its-own-freemium-deep-research-product/) |
| **"速度够用"的流速判据** | Databricks：**10 tokens/s/用户 ≈ 450 wpm**，已快于常人阅读速度；TPOT 100 ms/tok 即达该阈值 | [Databricks](https://www.databricks.com/blog/llm-inference-performance-engineering-best-practices) |
| **确定性路径（非 LLM）** | OPA：低延迟策略判定预算 **~1 ms**；实测 **5–30 µs**（稳态） | [OPA](https://www.openpolicyagent.org/docs/latest/policy-performance/) |

> 注：上表 1–3 s 与 3–10 s 两档的边界来自 NN/g 的 1 s / 10 s 两个硬阈值及其"2–10 s 可不加进度条"的论述，NN/g 原文并未使用"流畅/可容忍"这类命名，命名仅为归纳。
