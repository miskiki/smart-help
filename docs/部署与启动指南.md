# 部署与启动指南

面向第一次在**新机器**上把本系统跑起来的同事。所有命令默认在**项目根目录**执行；`<项目根>` 表示你克隆代码的目录（示例：`/opt/smart-help` 或 `~/smart-help`）。
若只是日常启停与体检，看 [README](../README.md) 第 7 节即可；需要恢复数据与密钥，配合 [数据准备与目录说明](数据准备与目录说明.md) 一起看。

> 本指南只描述**事实与步骤**，不含任何真实口令/密钥。需要填写处统一写作 `CHANGE_ME`。

## 0. 适用环境与前置条件

### 0.1 操作系统与硬件

| 项 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Ubuntu 24.04 LTS（x86_64） | 其它 Linux 发行版未验证 |
| GPU | NVIDIA，Blackwell 架构（示例机 RTX 6000D，sm_120），驱动 595 系列 | 更低架构也能跑，但 `llama-server` 需对应架构的编译产物 |
| CUDA | 13.x runtime（与 PyTorch / llama.cpp 构建一致） | 只影响 GPU 侧 Python 与源码编译，纯部署可不装 toolkit |
| 内存 | ≥ 64 GB；示例机 251 GB / 96 vCPU | 加载 22 GB 的 35B GGUF 与多进程时有内存缓冲 |
| 显存 | 示例机 RTX 6000D 单卡约 **84 GB**（`nvidia-smi` 显示 85,651 MiB）；三个 GGUF 合计约 27 GB，加载后实际占用以 `nvidia-smi` 为准，规划时按 **≥ 48 GB** 预留 | 不足会分层卸载到 CPU，解码速度断崖下降 |
| 磁盘 | 项目约 3.6 GB；模型约 28 GB；数据与日志另计 → 建议 **≥ 100 GB** 空闲 | 备份、导出、链路日志会持续增长 |
| 系统包 | `build-essential libpq-dev libgomp1 git curl unzip rsync ca-certificates` | `libpq-dev` 是 `psycopg2-binary` 的兜底依赖 |

安装系统包：

```bash
sudo apt update
sudo apt install -y build-essential libpq-dev libgomp1 git curl unzip rsync ca-certificates
```

> 不要执行 `ubuntu-drivers install` 或卸载厂商驱动；示例机已验证 595 驱动可直接使用。

### 0.2 端口清单

| 端口 | 用途 | 监听 | 备注 |
|---|---|---|---|
| 5000 | Web（Gunicorn `app:app`） | `WEB_BIND_HOST`，默认 `127.0.0.1`；设 `0.0.0.0` 对局域网开放 | 页面与 API 共用 |

| 8095 | 嵌入服务（2560 维） | 仅 `127.0.0.1` | llama-server `--embeddings` |

## 2. 恢复私密数据

私密数据在项目外的 U 盘包 `smart-help-private-data/` 中，结构约定：

```text
smart-help-private-data/
├─ restore/                    # 按项目相对路径组织，可直接覆盖到项目根
│   ├─ data/...
│   ├─ src/data/policy_evidence/...
│   ├─ models/qwen3-embedding-4b/...
│   ├─ deploy/web.env
│   ├─ deploy/web.gray.env
│   └─ config/model_settings.yaml
├─ MANIFEST-SHA256.txt         # 全部交付文件的 sha256
└─ README（说明版本与交接人）
```

步骤：

```bash
# 1) 挂载 U 盘（设备名以 lsblk 为准）
lsblk
sudo mkdir -p /media/usb && sudo mount /dev/sdX1 /media/usb

# 2) 先校验交付完整性（大文件耗时较长，可先跑小文件）
cd /media/usb/smart-help-private-data
sha256sum -c MANIFEST-SHA256.txt

# 3) 恢复到项目根（-a 保留时间戳与权限）
cd <项目根>
rsync -a /media/usb/smart-help-private-data/restore/ ./
# 等价写法：cp -a /media/usb/smart-help-private-data/restore/. <项目根>/

# 4) 收紧权限（配置含密钥、data 与 src/data 含个人信息）
chmod 600 deploy/web.env deploy/web.gray.env config/model_settings.yaml
chmod -R go-rwx data src/data models runtime run 2>/dev/null || true

# 5) 卸载 U 盘
sudo umount /media/usb
```

### 2.1 校验政策证据包引用的原始文件

`src/policy_core/local_evidence.py` 只对 `bundle.json` 中 `original_files` 登记的**少量文件**做逐字节 SHA256 校验（当前版本登记 2 个），校验失败只会让证据链降级、**不会导致启动失败**。恢复后建议主动核对一次：

```bash
cd <项目根>
python3 - <<'PY'
import hashlib, json, os
root = os.path.abspath('data')
bundle = json.load(open('src/data/policy_evidence/bundle.json', encoding='utf-8'))
bad = 0
for name, rec in bundle.get('original_files', {}).items():
    path = os.path.join(root, name)
    actual = hashlib.sha256(open(path, 'rb').read()).hexdigest() if os.path.isfile(path) else None
    ok = actual == rec.get('sha256')
    bad += 0 if ok else 1
    print(('OK  ' if ok else 'FAIL'), name)
print('校验失败数:', bad)
PY
```

### 2.2 必需 / 可选文件

完整的“文件 → 目标路径 → 用途 → 是否 SHA256 校验 → 敏感级别 → 缺失后果”契约表见 [数据准备与目录说明](数据准备与目录说明.md)。最小可启动集合是：

- `data/policy_db/smart_policy.db`（SQLite 回退库）
- `src/data/policy_evidence/bundle.json`
- `models/qwen3-embedding-4b/tokenizer.json` + `sentence_bert_config.json`（仓库内已有）
- `deploy/web.env`、`config/model_settings.yaml`
- `data/` 根目录的全部 `.xlsx/.wps/.docx` 业务文件（缺失不阻塞启动，但证据链与规则编译会降级）

> `data/` 根目录业务文件**不能改名、不能挪到子目录**：证据包按文件名定位并校验 SHA256，改名等价于缺失。分类占位目录（`data/个人信息数据/`、`data/政策数据/`）只是说明文件，真实文件仍放原路径。

| 变量 | 含义 | 填写示例 / 注意 |

### 3.3 `config/model_settings.yaml` 必填项

模板 `config/model_settings.example.yaml` 已给出四个平台，按实际删改：

| 平台 | 用途 | 关键字段 |
|---|---|---|
| `bailian` | 可选云端（百炼，OpenAI 兼容） | `api_key: CHANGE_ME_YOUR_DASHSCOPE_API_KEY`；`embed_dim: 1536`；`rerank_endpoint` |
| `local-qwen3-emb` | 本地嵌入 + 重排 | `base_url: http://127.0.0.1:8095/v1`；`embed_dim: 2560`；`rerank_endpoint: http://127.0.0.1:8096/v1/rerank` |

## 5. 数据库准备与迁移

### 5.1 启动 Kingbase 并确认连通

```bash
# 服务名随安装方式不同：LSB 安装通常是 kingbased，systemd 安装可能是 kingbase
systemctl status kingbased || systemctl status kingbase
sudo systemctl start kingbased            # 或 sudo /etc/init.d/kingbased start

ss -tln | grep ':54321 '                  # 应看到 127.0.0.1:54321
```

用安装目录下的客户端连接（示例路径 `/opt/Kingbase/ES/V8/Server/bin`）：

```bash
/opt/Kingbase/ES/V8/Server/bin/ksql -h 127.0.0.1 -p 54321 -U system -d policy_db_mig20261021 -c 'select 1;'
```

> Kingbase 在示例环境为 **V008R006C008B0014、Oracle 兼容模式、UTF8 / C / C**。应用通过 psycopg2 连接，**不要把库改成 PG 兼容模式**，也不要在原库上原地改名。

### 5.2 建空库与业务账号（从备份恢复时）

```sql
-- 以 system（库属主）执行
CREATE DATABASE policy_db_mig20261021
  WITH ENCODING 'UTF8' LC_COLLATE 'C' LC_CTYPE 'C' TEMPLATE template0;
CREATE DATABASE smart_help_auth_mig20261021
  WITH ENCODING 'UTF8' LC_COLLATE 'C' LC_CTYPE 'C' TEMPLATE template0;

CREATE USER smart_help_policy WITH PASSWORD 'CHANGE_ME';
CREATE USER smart_help_auth_app WITH PASSWORD 'CHANGE_ME';

GRANT CONNECT ON DATABASE policy_db_mig20261021 TO smart_help_policy;
GRANT CONNECT ON DATABASE smart_help_auth_mig20261021 TO smart_help_auth_app;
```

再分别连到两个库内授权：

```sql
GRANT USAGE ON SCHEMA public TO <应用账号>;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO <应用账号>;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO <应用账号>;
```

> 语法提示：上面是 PG 风格写法；Kingbase 在 **Oracle 兼容模式**下通常也接受 `CREATE USER <name> IDENTIFIED BY '<口令>'`。两种写法任选其一，以 `ksql` 实际执行结果为准。若备份文件的属主是 `system`，恢复时保留 `--no-owner`（见 §5.3），再用上面的 `GRANT` 授权给应用账号。注意应用账号的权限边界：对 `system` 属主的表只有 DML 权限（所以 `qa_log` 这类表不能 ALTER，`qa_trace` 才单独建表），但需要在 `public` schema 有 `CREATE` 权限，否则 §5.4 的迁移脚本建表会失败。

### 5.3 恢复数据

```bash
# 政策库
/opt/Kingbase/ES/V8/Server/bin/sys_restore \
  -h 127.0.0.1 -p 54321 -U system -W \
  --exit-on-error --single-transaction --no-owner --no-privileges \
  -d policy_db_mig20261021 /path/to/policy_db.dump

# 账号库
/opt/Kingbase/ES/V8/Server/bin/sys_restore \
  -h 127.0.0.1 -p 54321 -U system -W \
  --exit-on-error --single-transaction --no-owner --no-privileges \
  -d smart_help_auth_mig20261021 /path/to/smart_help_auth.dump
```

对账与验收：检查退出码为 0、日志无失败项，再用业务账号 `select count(*)` 抽查关键表（`policy`、`policy_vector_qwen3`、`policy_rule`、`admin_user`、`qa_log`）。

> **禁止**使用旧的 `admin_panel/migrate_to_kingbase.py`（会 `DROP TABLE ... CASCADE`，只覆盖旧表清单，且依赖 Windows 路径）。

### 5.4 结构迁移脚本（幂等，先检查再执行）

迁移脚本默认只读检查，`--apply` 才真正动库；重复执行无副作用。推荐顺序：

```bash
cd <项目根>
python deploy/migrate_policy_admin.py --apply      # outbox / import_batch / import_row / policy_scope 表；policy.deleted_at 列
python deploy/migrate_policy_scope.py --apply      # policy_scope 结构化地区范围回填（依赖上一步建表）
python deploy/migrate_models.py --apply            # models 表 + 部分唯一索引；audit_log.target_code 列宽 32→64
python deploy/seed_models.py --apply               # 把 model_settings.yaml 的对话平台导入 models 表（依赖 models 表）
python deploy/migrate_m0.py                        # qa_trace 表与索引（幂等；--dry-run 只检查）
python deploy/migrate_vector_multi_model.py --apply  # 向量表主键 (id) → (id, embed_model)
```

| 脚本 | 作用 | 顺序理由 | 注意 |
|---|---|---|---|
| `migrate_policy_admin.py` | 生命周期/导入/scope 表与软删列 | 先建表 | 应用账号非属主，脚本用 `IF NOT EXISTS` 风格 DDL |
| `migrate_policy_scope.py` | 回填 `policy_scope` | 依赖 `policy_scope` 表已存在 | 默认 dry-run，报告全库回填情况 |
| `migrate_models.py` | `models` 注册表 | 先建表 | SQLite 新环境按 ORM 定义直接建表 |
| `seed_models.py` | 模型行 seed | 依赖 `models` 表 | 按稳定 id 跳过已存在行 |
| `migrate_m0.py` | `qa_trace` 回放映射表 | 独立 | `qa_log` 归库属主所有，应用账号无 ALTER 权限 |
| `migrate_vector_multi_model.py` | 向量表复合主键 | 独立 | 已迁完再跑为“无变更” |

### 5.5 账号库与管理员初始化

账号表（`admin_user`、`qa_log`、`conversation`、`login_session`、`auth_audit`、`survey_result`、`delete_confirmation`）随**账号库备份**恢复带入，仓库不提供 `create_all` 式初始化脚本（`src/seed.py` 会直接抛错，禁止自动生成演示账号）。
初始化 / 恢复管理员（需表已存在，建议在服务停止时执行）：

```bash
cd <项目根>/src
python manage_auth.py admin
```

它会交互式要求：用户名、真实姓名、临时密码（不回显），并强制该账号首次登录修改密码。另有 `python manage_auth.py recover-interrupted`（服务停止时把卡在 `generating` 的问答标记为中断）。

> 从零建一个**全新的空账号库**时，需要 DBA 按 `src/models.py` 的表定义建表（本仓库当前没有对应迁移脚本）——这一点**待确认**，请先向交接人索取账号库 dump。

### 5.6 SQLite 回退模式

不配置 `ADMIN_DB_URL`（且不设 `USE_KINGBASE=1`）时，`src/config.py` 回退到：


限制：`SMART_HELP_AUTH_DATABASE_URL` 仍是**必填**（否则应用启动即报错）；SQLite 只适合本地演示/无金仓时的降级使用，生产以 Kingbase 为准。

## 6. 模型准备

### 6.1 文件清单

| 文件 | 大小（约） | 用途 | 配置变量 |
|---|---|---|---|
| `llama-server`（源码编译版） | 92 MB | 推理进程 | `LOCAL_LLM_SERVER` |
| `Qwen3.6-35B-A3B-UD-Q4_K_M_MTP.gguf` | 22 GB | 作答模型 | `LOCAL_LLM_MODEL` |
| `Qwen3-Embedding-4B-Q4_K_M.gguf` | 2.4 GB | 嵌入（2560 维） | `LOCAL_EMBED_GGUF` |
| `Qwen3-Reranker-4B.Q4_K_M.gguf` | 2.6 GB | 重排 | `LOCAL_RERANK_GGUF` |
| `models/qwen3-embedding-4b/tokenizer.json` | 11 MB | token 预算（精确截断） | 固定路径；缺失时 `foreground.py` 自动下载 |
| `models/qwen3-embedding-4b/sentence_bert_config.json` | 极小 | 嵌入配置 | 固定路径；缺失时自动生成 |

模型可以放在项目外的任意目录（例如 `/opt/models/`），用 `deploy/web.env` 的四个变量指过去即可；**不要提交进 Git**。

### 6.2 llama-server 要求

必须是**含目标 GPU 架构 kernel 的源码编译版**。示例机的教训：官方预编译包 `llama-b11753` 缺 Blackwell sm_120 kernel，同模型同参数下纯解码只有 87.7 tok/s；换源码编译版（CUDA 13.2 + `nvcc`）后为 225.6 tok/s。注意本机速度随运行状态波动较大（实测 108–213 tok/s），**验收以当时基准为准**，用 `bash deploy/llm_speed_probe.sh` 取样，不要用历史数字承诺。重编译步骤见 [Ubuntu 迁移部署指南 §9](Ubuntu24.04_RTX6000D_Conda_Kingbase迁移部署指南_20261020.md)。

`deploy/local_llm.py` 中的关键参数（不要随意改）：

| 参数 | 值 | 原因 |
|---|---|---|
| `--gpu-layers` | `all` | 全量上 GPU |
| `--ctx-size` | `65536`（总池） | 单请求 = `65536 ÷ --parallel 4 = 16384`，应用 prompt 约 5.4–5.8k，必须 ≥ 16384 |
| `--parallel` | `4` | 与 ctx-size 联动 |
| `--flash-attn` | `on` | 显存与速度 |
| `--spec-type draft-mtp` / `--spec-draft-n-max 2` | 2 | MTP 投机解码，实测最优 |
| `--predict` | `4096` | 单次生成上限 |

### 6.3 验证

```bash
curl -s http://127.0.0.1:8081/health
curl -s http://127.0.0.1:8081/props | python3 -c "import json,sys;d=json.load(sys.stdin);print('n_ctx=',(d.get('default_generation_settings') or {}).get('n_ctx'),'slots=',d.get('total_slots'))"
curl -s http://127.0.0.1:8095/health
curl -s http://127.0.0.1:8097/health

```

`n_ctx` 必须 ≥ 16384，否则 `foreground.py` 会在启动时自检失败并退出。

## 7. 启动与验收

### 7.1 `deploy/start.sh` 做了什么

1. `cd` 到项目根，`set -a` 载入 `deploy/web.env`，导出 `CHAIN_TRACE_STDOUT=1`；
2. 预检：`llama-server` 可执行、作答 GGUF、`config/model_settings.yaml`、`src/rule_worker.py`、嵌入/重排 GGUF；
3. 预检端口 8081 / 8095 / 8096 / 8097 / 5000 未被占用（**不接管、不终止未知进程**）；
4. 打印向量与模型信息；
5. `exec` 到 `deploy/foreground.py`，由它按序拉起并守护：

```text
8081 作答模型（最长等 240 s）→ /props 上下文自检
  → 8095 嵌入（≤240 s）→ 8097 重排（≤240 s）→ 8096 兼容层（≤90 s）
  → 5000 Gunicorn（探 /ask，≤60 s）
  → 规则 worker（--watch）
```

任一致命组件退出会整体停服；规则 worker 退出只告警并按 3s×N（上限 60s）退避重启，不停服。

### 7.2 启动

```bash
cd <项目根>
bash deploy/start.sh
```

前台运行，日志直接打在终端，同时写入：

- `runtime/logs/service_8081.log`、`service_8095.log`、`service_8096.log`、`service_8097.log`、`service_5000.log`
- `runtime/logs/chain_trace-<pid>.jsonl`（链路追踪）
- pid：`runtime/foreground.pid`；锁：`runtime/foreground.lock`

### 7.3 验收

```bash
bash deploy/status.sh
```

六段输出，逐段应为 ✓：

| 段 | 检查内容 |
|---|---|
| 前置依赖 | llama-server、三个 GGUF、tokenizer、`config/model_settings.yaml` |
| 服务 | 8081/8095/8096/8097 `/health`、5000 `/` = 200、`rule_worker.py --watch` 进程 |
| 数据库 / 规则库 | 金仓连通；作答模型平台、向量平台、索引维度（2560）、读取表；规则库条数与地区分布 |
| 守护 / 自启 | `autostart.sh` 守护进程、cron 自启是否安装 |
| 当前速度 | 3 次解码采样（tok/s） |
| 结论 | ✅ 系统正常 / ⚠️ 附异常清单 |

页面与 API 抽查：

```bash
curl -s -o /dev/null -w 'GET /      -> %{http_code}\n' http://127.0.0.1:5000/
curl -s -o /dev/null -w 'GET /ask   -> %{http_code}\n' http://127.0.0.1:5000/ask
```

浏览器打开 `http://<主机>:5000/ask`（`WEB_BIND_HOST=0.0.0.0` 时局域网可访问；否则先做 SSH 端口转发：`ssh -L 5000:127.0.0.1:5000 <用户>@<主机>`）。

## 8. 停止 / 重启 / 开机自启

```bash
bash deploy/stop.sh          # 停 foreground 及其子进程；Kingbase 不受影响
bash deploy/start.sh         # 再次启动即为重启
```

`stop.py` 只停止 `runtime/foreground.pid` 记录、且 uid/cwd/cmdline 都对得上的进程，最多等 25 s；不会误杀其它进程。

开机自启（用户级 cron，无需 root、无需登录）：

```bash
bash deploy/install_autostart.sh         # 安装并立即启动守护
bash deploy/install_autostart.sh --status
bash deploy/install_autostart.sh --remove
```

- cron 条目：`@reboot sleep 25; cd <项目根> && bash deploy/autostart.sh --daemon >> runtime/logs/autostart.log 2>&1`
- 守护循环：`start.sh` 退出后按 10s → 最长 300s 退避重启；单实例（`flock`）；pid `runtime/autostart.pid`
- 日志：`runtime/logs/autostart.log`（超过 50 MB 轮转为 `.1`）

重载代码的推荐方式：前台终端 `Ctrl+C`（或 `bash deploy/stop.sh`）后重新 `bash deploy/start.sh`。
Gunicorn 支持 `kill -HUP <gunicorn 主进程>` 优雅重载 Web（不动模型栈），但**不要**直接 kill 8081/8095/8097：它们是 foreground 的致命子进程，任一退出会触发整体停服。

systemd 方案（可选，历史模板）：`docs/deploy_ubuntu24_20261020/smart-help-web.service.example`、`smart-help-model.service.example`。当前生产使用 `start.sh` + cron 自启，模板仅在使用 systemd 托管时参考。

## 9. 灰度发布（只读全国实例，可选）

灰度 = 同一份代码 + 同一个库（只读用途）+ 独立进程 5001 + 只读全国开关；**生产 5000 不动**（不 HUP、不重启、不改 `web.env`）。

前置条件：5001 空闲、5000 健康、`deploy/web.env` 存在、`runtime/` 可写。

```bash
cd <项目根>
cp deploy/web.env deploy/web.gray.env
cat deploy/web.gray.env.example >> deploy/web.gray.env
chmod 600 deploy/web.gray.env

bash deploy/gray_up.sh          # 启动 5001（只读守卫不通过会拒绝启动）
bash deploy/gray_status.sh      # 进程/端口/HTTP/关键开关；退出码 0=健康
bash deploy/gray_down.sh        # 只停 gray.pid 指向的 gunicorn，不影响 5000
```

`gray_up.sh` 的硬性守卫：`GRAY_BIND` 必须是 `127.0.0.1` 且不能是 5000；`SERVICE_SCOPE=national`、`REGION_NATIONWIDE=1`、`NATIONAL_READONLY=1`、`POLICY_SCOPE=1`，且 `POLICY_LIFECYCLE/POLICY_IMPORT/POLICY_AUTOPILOT/POLICY_WORKER=0`（设 `GRAY_ALLOW_WRITES=1` 可跳过守卫，仅用于调试，不要在生产用）。

已知副作用：认证库不是只读——问答仍会写 `conversation` / `qa_log` / `qa_trace`。因此灰度应使用测试账号并在结束后清理。

## 10. 常见故障与处置

| # | 现象 | 排查命令 | 原因 | 处理 |
|---|---|---|---|---|
| 1 | `start.sh` 打印“启动预检失败：llama-server 不存在或不可执行” | `ls -l "$LOCAL_LLM_SERVER"` | 路径错 / 未 `chmod +x` / 用了预编译版 | 配 `LOCAL_LLM_SERVER` 或编译 sm_120 版 |
| 2 | “作答模型不存在”“缺少嵌入模型”“缺少重排模型” | `ls -lh` 对应 GGUF | 模型未拷入 / 变量为空 | 恢复模型并在 `web.env` 中指向 |
| 3 | “端口 xxx 已被占用” | `ss -tlnp \| grep -E ':(5000\|8081\|8095\|8096\|8097) '` | 上次未停干净或有其它进程占用 | `bash deploy/stop.sh`；确认可停后 kill 占用进程，或改端口（需同步改 `foreground.py`/`local_llm.py`） |
| 4 | “缺少模型配置 config/model_settings.yaml” | `ls -l config/` | 未从模板生成 | `cp config/model_settings.example.yaml config/model_settings.yaml` 并填写 |
| 5 | 8081 起不来 / `/health` 不 200 | `tail -100 runtime/logs/service_8081.log`；`nvidia-smi` | 显存不足、GGUF 损坏、二进制与 GPU 架构不匹配 | 释放显存；重下模型；换对应架构编译版 |
| 6 | 8081 起来了但启动器退出：`单请求上下文仅 N token` | `curl -s 127.0.0.1:8081/props` | `--ctx-size` 未按 `parallel × 16384` 配置 | 改 `deploy/local_llm.py` 的 `ctx-size`/`parallel`，重启 |
| 7 | Web 启动报 `请先运行账号数据库迁移初始化命令` | 检查 `web.env` 的 `AUTH_DATABASE_URL`、`SMART_HELP_AUTH_JWT_SECRET` | 认证库未配，或 JWT secret < 32 字符 | 补齐配置；重新生成 `openssl rand -hex 32` |
| 8 | `password authentication failed` / `could not connect to server` | `bash deploy/status.sh`；用 `ksql` 手连 | 连接串错、口令特殊字符未编码、Kingbase 未启动 | 修 `ADMIN_DB_URL`（URL 编码）；`systemctl start kingbased` |
| 9 | `must be owner of table qa_log` | 迁移日志 | 应用账号非表属主 | 不要用应用账号 ALTER `qa_log`；回放映射走 `qa_trace`（`migrate_m0.py`） |
| 10 | 页面正常但卡片没有政策依据 / 证据标注“缺失” | `grep -E 'local_evidence_bundle_(missing\|invalid)\|original_file_changed_or_missing' runtime/logs/*.log` | `bundle.json` 缺失，或 `data/` 根文件改名/被替换（SHA256 不符） | 按第 2 节恢复原文件；`original_sheet_mismatch` 说明表格结构变了 |
| 11 | 检索不到政策 / 卡片为空 | `bash deploy/status.sh` 看“向量平台、索引维度、读取表” | 8095 未起；`EMBED_PLATFORM` / `POLICY_VECTOR_TABLE` 与库不一致；`app_config.qa_embed_platform` 错 | 修配置；必要时 `RULE_ENGINE=off` 临时回退；重建向量见 `src/reindex_vectors_2560.py` |
| 12 | 服务整体退出，日志显示“服务进程 N 退出” | `tail runtime/logs/service_*.log` | 8081/8095/8096/8097/5000 任一崩溃 | 修崩溃组件后重启；规则 worker 崩溃不会停服 |
| 13 | 规则库不更新 / 新县区无规则 | `pgrep -f 'rule_worker.py --watch'`；`tail runtime/logs/autostart.log` | worker 未起、任务积压、`RULE_WORKER_INTERVAL` 大 | 重启拉起；可手动 `python src/compile_rules.py --help` 补编译 |
| 14 | 回答很慢（< 100 tok/s） | `bash deploy/status.sh` 测速；`nvidia-smi`；`deploy/llm_speed_probe.sh` | GPU 被占用、模型分层到 CPU、非 sm_120 编译版 | 停占用进程；确认 `--gpu-layers all`；换编译版 |
| 15 | 局域网访问不了 | `ss -tln \| grep :5000`；`sudo ufw status` | `WEB_BIND_HOST` 仍是 127.0.0.1；防火墙未放行 | 设 `WEB_BIND_HOST=0.0.0.0` 重启；`sudo ufw allow 5000/tcp` |
| 16 | 页面 502 / 长时间无响应（Nginx） | `curl -s -o /dev/null -w '%{http_code}' 127.0.0.1:5000/` | Web 未起；`proxy_read_timeout` 小于 600s | 起 Web；模板已设 600s，确认未被改写 |
| 17 | 开机后服务没起来 | `bash deploy/install_autostart.sh --status`；`tail runtime/logs/autostart.log` | cron 未安装 / 环境变量不生效（cron 不加载 shell profile） | 重装自启；确保 `web.env` 里已写全路径 |
| 18 | 磁盘满导致启动失败 | `df -h <项目根>`；`du -sh runtime/logs data/policy_db/exports` | 链路日志/导出堆积 | 清理并按需轮转日志（`autostart.log` 自动轮转，`service_*.log` 每次启动覆盖） |

## 11. 安全与合规

### 11.1 不得入库的内容

`deploy/web.env`、`deploy/web.gray.env`、`config/model_settings.yaml`、`data/` 下业务数据、`src/data/policy_evidence/`、模型权重、导出文件、运行日志、`docs/history/` 都不进 Git（`.gitignore` 已排除）。提交前自检：

```bash
git status --short
git check-ignore -v deploy/web.env config/model_settings.yaml
```

### 11.2 首启后建议轮换的密钥

| 密钥 | 位置 | 轮换影响 |
|---|---|---|
| 账号库口令（`smart_help_auth_app`） | Kingbase + `SMART_HELP_AUTH_DATABASE_URL` | 重启 Web 生效 |
| 政策库口令（`smart_help_policy`） | Kingbase + `ADMIN_DB_URL` | 重启 Web 生效 |
| `SMART_HELP_AUTH_JWT_SECRET` | `deploy/web.env` | 所有登录态立即失效，用户需重新登录 |
| `ADMIN_SECRET` | `deploy/web.env` | 后台 session 失效 |
| 云端模型平台 api_key | `config/model_settings.yaml` | 云端平台不可用，本地链路不受影响 |
| Kingbase `system` 管理员口令 | 数据库 | 仅运维使用，勿写入任何仓库文件 |

### 11.3 数据与交付

- 个人信息数据（监测对象表格、户匹配结果、问卷、问答日志）只放本机，权限收紧（`chmod -R go-rwx data src/data`）。
- 日志与链路追踪同样含敏感信息（`runtime/logs/chain_trace-*.jsonl`、`src/logs/`），对外提供日志前先脱敏。
- U 盘私密包交接：交付前后都跑 `sha256sum -c MANIFEST-SHA256.txt`；交接完成后销毁 U 盘副本或加密保存。
- 公网暴露前必须：修改全部默认密钥、关闭 `/admin` 的匿名访问路径（登录鉴权已内置）、在反向代理层加 HTTPS 与访问控制；本系统默认只监听回环地址。
- 云端模型平台会把提问文本发往外部服务；有 PII 合规要求时只启用本地模型平台。
